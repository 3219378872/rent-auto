# 事故复盘：0002 迁移 up 文件丢失导致假绿测试

日期：2026-08-23 ｜ 发现于：M5 里程碑 ｜ 严重级：高

## 时间线

1. M3 创建迁移时使用 shell `printf '-- ...'`，`--` 被当作参数 → up 文件**创建失败**，
   仅 down 文件成功；Write 工具的补写因当时目录混乱未真正落盘
2. M3 门控"通过"——因为：加载器只把存在 up 文件的版本计入列表；
   集成测试用的本地库残留着更早手工实验创建的业务表，掩盖了缺失
3. M3 推送时 pre-push 门控失败（另一幽灵文件问题），处理后推送成功——
   假绿状态随之进入 main
4. M5 新增 0003 迁移，全新数据库环境下 `listings does not exist` 暴露真相

## 根因

- 用 shell 字符串拼 SQL 文件（工具误用）
- 测试环境与迁移状态不隔离：库表先于迁移存在 → 测试无法证明迁移正确
- 加载器对"只有 down 没有 up"的半迁移静默忽略而非报错

## 修复与防御

1. 从记忆内容重建 0002_business.up.sql 并全量重验（本证据文档）
2. **加载器加固**：检测到 .down.sql 存在而对应 .up.sql 缺失时直接报错
   （store.LoadMigrations 增加 orphan-down 校验）
3. 集成测试前强制 schema 重置能力保留（DROP SCHEMA CASCADE 手册化于 runbook）
4. 教训入 AGENTS 工作流：生成迁移一律走 Write 工具/make migrate-new，禁止 shell 重定向拼 SQL

## 影响评估

main 分支 bb2e9b7 及之前的部署若从零建库会在启动迁移阶段失败
（0001 可用，业务表缺失）；已在本次提交修复，无生产部署受影响。
