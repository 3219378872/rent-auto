# 事故复盘：UU 短信验证失败把面板会话一起踢下线（401 语义撞车 + gzip 解码崩）

日期：2026-08-23 ｜ 发现于：真机验证短信上行修复 ｜ 严重级：中

## 现象

面板登录后进入渠道页，点击 UU 短信登录的「登录」按钮，整个面板被弹回
登录界面；重新登录后复现。

## 时间线（audit_log 实录）

```
06:32:50 channel.uu.login_failed "getUserInfo: http 200 non-json response"
06:32:52 login.success                       ← 用户被弹回后重新登录面板
06:33:02 channel.uu.sms_sent {"msg":"需进行图形校验","mode":"up"}
06:33:19 channel.uu.login_failed "decode: invalid character '\x1f'"
```

## 根因（三个独立缺陷叠加）

1. **401 语义撞车**：`POST /channels/uu/sms-verify` 失败返回 HTTP 401，
   前端拦截器将*任何* 401 视为面板会话过期 → 清 token 强跳 `#/login`。
   UU 平台拒绝验证码 ≠ 面板未登录
2. **gzip 透明解压被禁用**：`generateHeaders` 手动携带
   `accept-encoding: gzip`，Go net/http 对手动设置该头的请求不做自动解压，
   平台返回的 gzip 响应体直达 JSON 解码器（`\x1f` 魔数报错）——
   06:32:50 的 non-json 与 06:33:19 的 `\x1f` 均为此因
3. **风控误分类**：平台对高频重试回「需进行图形校验」（Code=0），Msg 判定
   逻辑将其归入 up 模式，前端误导用户执行短信上行（实际需图形验证码）

## 修复与防御

1. sms-verify 失败改回 **400 verify_failed**；前端拦截器仅在
   `code === 'unauthorized'` 时强制登出（双层防御）
2. generateHeaders 移除手动 accept-encoding（api-notes 补充约定 #13）；
   mock 测试 `TestSmsSignInGzipBody` 以真实 gzip 响应回归
3. SendLoginSmsCode 对「图形校验/滑块」文案单独报错并置 Mode=""，
   `TestSMSSendCaptchaBlocked` 覆盖；api-notes 认证节记录该风控行为

## 影响评估

仅影响面板内 UU 短信登录引导流程；无资金/货架写操作风险。
风控图形校验为平台侧限制，无法自动化——用户需换网络环境或稍后重试，
后续可评估接入 UU App 扫码登录作为替代路径（非目标暂缓）。
